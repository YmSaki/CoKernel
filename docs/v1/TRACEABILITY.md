## Canonical requirement-to-evidence checkpoints

### Environment correctness

Requirements: R-PROJ-004/005/006, R-ENV-001..006, R-EXEC-001.

Evidence:

1. create Project;
2. add pinned/lightweight dependency through CoKernel;
3. verify lock/environment generated by uv;
4. start Session and import dependency;
5. mutate Project package state;
6. verify old Session remains alive but becomes environment-stale;
7. restart and verify new environment state.

### Notebook import compatibility

Requirements: R-NB-001..009.

Evidence:

1. Windows-selected fixture with Markdown/code/output/attachment/unknown metadata;
2. controlled transfer into Project;
3. round-trip preservation rules pass;
4. Project determines execution environment;
5. execution output saves atomically;
6. external modification yields conflict rather than silent overwrite.

### Parallel Session semantics

Requirements: R-EXEC-005..012, R-QUAL-003.

Evidence:

- same Session submissions execute FIFO;
- two Sessions overlap in time;
- namespaces are isolated;
- crash of one worker leaves another alive.

### Human/AI shared state

Requirements: R-AI-001..005, R-MCP-001..006.

Evidence:

```python
secret_from_master = 123456789
```

Human executes it; MCP `get_variable` against the notebook primary Session returns the same value with the same worker identity and without creating another worker.

### Remote access isolation

Requirements: R-TUN-001..005, R-SEC-003/005.

Evidence:

- remote MCP works through tunnel;
- no public inbound port required;
- tunnel credentials absent from worker argv/env/log/diagnostics;
- disconnect tunnel -> local Session continues;
- reconnect -> remote access returns.

### Failure observability

Requirements: R-SUP-001..006, R-QUAL-005.

Evidence:

- force worker termination;
- Session becomes CRASHED;
- exit/signal/last operation/resource evidence captured;
- unknown root cause is labeled unknown rather than fabricated;
- UI offers explicit recovery action.

### Maintenance safety

Requirements: R-UPD-001..004, R-INST-007.

Evidence:

- disruptive update detects active Session and defers/prompts;
- v1 update preserves Project files;
- repair preserves Project files;
- legacy reset requires explicit destructive path and is tested only on disposable old runtime.

## Release traceability rule

A P0 requirement may not be marked complete solely because code exists. It requires at least one automated or real-machine acceptance artifact identified by `TEST_ACCEPTANCE.md`.

If implementation discovers a requirement cannot be satisfied as written, update the requirement/design and rationale explicitly rather than silently weakening the test.
